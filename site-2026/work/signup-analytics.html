Case study 01 · Church-tech SaaS

Making signup analytics trustworthy before a production cutover

Marketing was about to switch signup reporting from a staging analytics property to production. Before that happened, I had to prove the numbers were real. I audited the pipeline myself, found three silent bugs, decided the order to fix them, and only then shipped the change.

Industry
Church-tech SaaS
Role
Engineering lead, hands-on
Team
Leading a 15-person outsourced team
Stack
GA4 · PostHog · Google Tag Manager · SQL

My role and responsibilities

  • Owned the signup analytics cutover end to end, from audit to production.
  • Ran the production QA pass on the signup instrumentation myself.
  • Audited the Tag Manager container by hand: tags, triggers, duplicates and custom-dimension slots.
  • Reconciled backend and frontend event names so both tools described the same moments.

Key decisions

  • Rank issues by irreversibility, not by noise. Anything that would permanently corrupt history had to be fixed first.
  • Delay the cutover on purpose. Bot traffic (load-balancer health checks and a security scanner) was inflating signups; going live first would have put phantom users in marketing reports.
  • Author the production change myself. I wrote and published the Tag Manager version that moved signup events to the real property, and registered the custom dimensions it needed.
  • Verify with live data, not trust. I watched live event counts after publishing, and corrected my own misread of the Realtime window before it became a wrong claim.

What we built

  • Bot inflation fixed. Health checks and scanner traffic no longer count as signups.
  • A 3.3× over-count explained. An event-mapping gate checked a state ("is submitted") instead of a transition ("just became submitted"), so one event fired again on every later update.
  • Lost attribution restored. Campaign attribution was missing for 100% of persons because of one missing PostHog setting (person_profiles: 'always').
  • Cost analysis without the API. When the billing API returned a 403, I worked out the cost tiers directly with SQL on the event data.

The hard part

The hard part wasn't the switch. It was knowing which numbers to trust when two tools disagreed, and resisting the pressure to ship before the data was clean.

What I learned

"The dashboard doesn't show the answer" is where the work starts. I check every claim against live data before acting on it, including my own.
