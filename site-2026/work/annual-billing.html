Case study 02 · Church-tech SaaS

De-risking an annual billing launch with a fixed deadline

A revenue-critical program with an external deadline: annual pricing for new customers by January 1, 2027. My job was to make sure what the team said the system does matched what the code actually does, before customers found the gap.

Industry
Church-tech SaaS
Role
Engineering lead, program owner
Team
Leading a 15-person outsourced team
Domain
Subscriptions · billing · onboarding

My role and responsibilities

  • Owned the program on the engineering side, tracking risk at the mechanism level, not just ticket status.
  • Read pull request diffs and code paths myself instead of relaying assumptions.
  • Reported risk upward at the planning-increment level, in a format leadership could act on.

Key decisions

  • Trust the code over the meeting notes. Notes said switching billing cadence deletes and recreates the subscription; the code actually swaps items on the existing subscription. Proration, history and reporting depend on which one is real, so I raised it with the code as evidence.
  • Flag unticketed scope early. Following the customer path end to end, I found that choosing a plan after onboarding verification had no ticket at all, and raised it while there was still room in the plan.

What we built

  • A shared, correct model of billing behavior. The team plans against how the system really behaves.
  • Hidden scope on the board. Instead of a late surprise close to the deadline.

The hard part

Billing changes are unforgiving: a wrong assumption shows up as a wrong charge on a real card. The work cuts across several squads, so shared understanding is a risk in itself.

What I learned

On a billing project, the most expensive bug is a shared wrong assumption. The program is still in progress, with fewer unknowns.
