Case study 05 · Tithely · Billing

Annual billing, de-risked before it ships.

A revenue-critical program with a fixed date: new customers on annual pricing by January 1, 2027. My job was to make sure what we said the system does matched what the code actually does, before customers found the gap.

Role
Engineering lead, program owner
Org
Tithely · EPD
When
2026 — in progress
Domain
Subscriptions · billing · KYC

A billing change with no room to slip.

Tithely plans in Planning Increments, and annual billing is one of the initiatives leadership is tracking. It has an external deadline: annual pricing for new customers by January 1, 2027. Billing changes are unforgiving. A wrong assumption shows up as a wrong charge on a real customer's card.

The work cuts across subscriptions, plan selection and the KYC onboarding flow, and several squads and stakeholders are involved, so shared understanding is a risk in itself.

The notes said one thing. The code did another.

In planning, meeting notes described what happens when a customer switches billing cadence (monthly ↔ annual): delete the subscription and create a new one. I went and read the code path. It doesn't do that at all.

That difference matters: swapping items on an existing subscription keeps the same subscription, history and identifiers. Delete-and-recreate doesn't. Downstream decisions about proration, reporting and edge cases were being made on the wrong model. I raised it with the code as evidence, so the team could plan against reality.

Finding the work nobody had ticketed.

Following the customer path end to end, I found a step that had no ticket at all: choosing a plan after KYC is submitted. Annual pricing for new customers has to work there too. Left alone, it would have surfaced late as a "surprise" blocker close to the deadline.

I flagged it as a scope risk early, while there was still room in the plan to absorb it.

How I run it

  1. Track mechanisms, not just status. A ticket marked "in progress" tells you little. I track the actual behavior each piece depends on, and where it could break.
  2. Verify against code. When notes, docs and code disagree, the code wins. I check pull request diffs and code paths myself instead of relaying assumptions.
  3. Surface risk early, upward. Risks go to leadership at the PI level in a clear, audience-calibrated format — before they become incidents.

In flight, with fewer unknowns.

The program is still in progress toward the January deadline. What changed is that the team is building against how the system really behaves, and the hidden scope is on the board instead of waiting to be discovered.
